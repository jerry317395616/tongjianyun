# 童健云膳食全流程 3D 工作台

本文件为膳食场景功能的设计、实施边界和交付说明。班级教师场景继续使用
`CLASSROOM_WORKBENCH.md`，不复制或替换教师业务。所有本期代码归属 `tongjianyun`。

## 1. 产品与入口

页面：`/tongjianyun-meal-scene`；支持 `?day=YYYY-MM-DD&meal=lunch`。
登录后从童健云角色入口选择“膳食全流程场景”，或从原业务工作台点击同名按钮。

这是一个完整 Three.js 场景，不是背景图片。建筑、内部桌台、人物、地面箭头和编号标签
属于同一场景；旋转、缩放、俯视、物件拾取以及等效键盘导航均可用。

默认只显示精简流程导航、日期/餐次、真实摘要和建筑标签，不把大量表格同时堆满屏幕。
点击建筑，才打开当前站点的业务面板；表格在屏幕空间保持水平可读，不倾斜贴进模型。

角色入口不等于角色授权。本期没有新建膳食角色，没有修改现有用户的角色或 DocPerm。
已有食谱、采购、收货、或完整库存读取能力的园内 System User 才能进入；各业务仍分别核验原权限。
仅有班级餐次权限的普通 Instructor 不会得到膳食管理入口；原纯教师默认进班级场景的逻辑保持。
管理员/原业务工作台用户可选择原入口或膳食入口，不把宽权限业务操作员推断为某个具体岗位。

## 2. 场景与业务顺序

```text
① 食谱与营养 → ② 食材采购 → ③ 到货与入库 → ④ 仓储管理
                                                       ↓
⑧ 追溯与报表 ← ⑦ 实际用餐确认 ← ⑥ 班级配餐 ← ⑤ 厨房备餐
```

地面路线、建筑编号、左侧导航及面板上一站/下一站使用同一有序索引。
编号描述业务顺序，不代表业务完成度。操作员可以回到任一站点，不能通过前进按钮自动确认事实。
预计人数是编谱采购的前置输入：顶部与第 6 站可先核对各班预计安排，实际就餐在第 7 站确认。
第 8 站的核对贯穿全过程，并不意味着只有流程最后才关注食品安全。

| 站点 | 当前实现 | 真实来源/复用服务 | 明确边界 |
| --- | --- | --- | --- |
| 1 食谱与营养 | 单份覆盖食谱直接打开周历；若所选日期没有覆盖食谱，也先显示五天 × 五餐的待选择周历；新建草稿及 Excel 导入均在场景内完成，导入先校对再明确保存；另可查看已有食谱和整周营养估算 | `recipe_storage.get_recipe_detail/save_recipe_payload`、`recipe_import`、`nutrition_sheet.get_nutrition_sheet` | 占位格不代表其他日期也未编排；点格只预览或编辑，不改变顶部业务日期/餐次；草稿不当发布；保存可能安排后台食材匹配，但不自动发布或采购；营养分类代表值不是单餐实测摄入或“食品安全合格率” |
| 2 食材采购 | 近七日可见订单；从已发布食谱核预计人数、物料和毛料换算，预览并明确创建需求草稿 | `recipe_procurement.default_scope/prepare/preview/create_request/revision_impact` | 只生成 Material Request 草稿；不下单、不自动收货、开票或付款；已有需求拒绝重复生成 |
| 3 到货与入库 | 近七日可见收货单；原单在场景面板内查看/核对 | `Purchase Receipt` 原表单 | 实际验收、部分收货、退货、提交和库存入账由原单处理；单据存在不是食品检验合格证明 |
| 4 仓储管理 | 切换有权仓库、分页查看账面数量/预计数量/已订未入库；原库存报表与物料维护 | `Warehouse`、`Item`、`Bin`、原 Stock Balance 报表 | 当前库存不随所选业务日期回溯；不同单位不合计；未虚构安全阈值、保质期或传感器数值 |
| 5 厨房备餐 | 已选择食谱的当前日期/餐次配方与每生带量；可打印参考 | 原食谱菜品/食材明细 | 尚无加工执行、温控、留样、消毒记录；不提供虚假开始/完成按钮 |
| 6 班级配餐 | 现有班级计划的预计/实际分列；完整性摘要；打印配餐参考 | `Tongjianyun Class Meal Confirmation` 的已保存快照 | 未保存不是零人；不是餐车轨迹、装车批次或送达签收；不公开幼儿健康详情 |
| 7 实际用餐确认 | 班级五餐明细、学生勾选、餐次批量草稿、预计保存/实际确认、原因与版本保护 | `classroom.get_meals/save_meals` → 原 `student_meals` | 沿用当前五餐整体确认规则，未实现独立逐餐完成状态；未来只能预计；不写考勤 |
| 8 追溯与报表 | 所选食谱的已有采购需求关联、原营养/采购/库存报表；未接入清单 | `revision_impact` 与原报表 | 不是产地、检验、批次、冷链全过程溯源；不显示“食安正常”或健康风险分数 |

采购、收货、仓库及已有食谱编辑/修订等原专业模块通过限定同源 iframe 按需打开，场景页面地址保持。第 1 站的新建与导入不再打开原模块。
模块内的保存、审批和提交仍是原流程。离开嵌入模块总会提示检查未保存修改，关闭后移除 iframe。
复杂原模块在手机内不适合嵌入或浏览器不允许加载时，保留清楚标注的“新页打开原模块”入口。
本期没有重新实现这些原生表单，也没有承诺所有历史专业单据只靠简化表格办理。

## 3. 事实、未知与范围

`meal_scene.get_overview` 只聚合当前有权读取的记录，不调用会初始化每日确认的
`daily_meals.get_daily_meal_confirmation` 或 `refresh_confirmation`。
打开场景、查询、换日期、旋转、选择建筑和勾选学生均不写业务记录。

预计汇总仅在全部可见班级都有已保存计划时给出；实际汇总仅在全部可见班级均已确认时给出。
否则传 `null` 并显示“待核对”，不会把部分班级人数冒充全园总数。
`confirmed_subtotal` 是明确命名的部分已确认人数，不用于顶部实际总数。
确认零人保留 `0`，无可见班级不能变成“100%完成”。

班级范围仍由现有权限和 `allowed_groups()` 交集决定。班级列表是当前启用班级，
餐次明细使用该日已保存名单快照，不能称为准确历史分班重建。
订单/收货按所选日期向前七日查询，每页 20 条，有下一页时标记“＋”；不把本页数量称为全量统计。
这些单据不全由食谱产生，因此明确注明“可见采购单据”，不能统称食谱履约进度。

库存先限定可见明细仓库与可读 Item，再分页查 Bin；不会先拿全部库存后在浏览器过滤。
库存读取显示实际读取时刻。账面数量、预计数量、已订未入库保留独立列，不将简单相减说成自动补货方案。
大规模物料场景应进一步优化可见 Item 索引查询，本期没有声称十万物料性能达标。

营养响应只保留原分析数值、规则元数据、标准名称、比例和说明，不把儿童人口明细发送到这个综合界面。
不读取病史、过敏说明或家长电话；“特殊餐执行闭环”仍明确列为未接入。

## 4. 提交、权限与并发

`require_access()` 校验已启用 System User 与已有业务权限。页面与 API 均独立校验，不依赖菜单隐藏。
个别站点缺少权限时显示“按权限开放”，而不是空表成功；不得以业务入口授予健康或财务权限。
个性化响应为 private/no-store，匿名访问固定回登录，拒绝由用户提供外部跳转目的地。

采购草稿创建只有显式 POST：

1. 读取并锁定原食谱，原服务重新校验发布日期、完整明细、公司/仓库与物料单位。
2. 使用原预览 token 重新校验食谱、人数和映射；本期不开放历史补录开关。
3. 查询现有需求并拒绝重复生成，旧单据不自动覆盖。
4. 只调用 `create_request`，不调用 `create_purchase`、`complete_purchase_cycle` 或 `recipe_execution.start`。

原预览中的单价是参考，维护价格可能发生变化；原需求单中仍须复核，不把预览当成锁价承诺。
原食谱专业模块保留其已有“发布并完成采购结算”功能，因此进入该模块前明确告知其业务影响。
本场景不会自动触发它，也不声称服务器已撤销原账号在原模块的权利。

五餐保存复用原服务的班级范围、完整唯一名单、未来日期限制、日锁定、修改原因和版本冲突校验。
列表按预计值形成的是本地草稿；只有明确提交才写入。勾选本身不保存。
网络超时会提示“保存结果未知”，要求先刷新原单，不自动重试写请求。
写入进行时阻止场景/日期切换和重复按钮操作；不同浮层、分页、仓库的异步回复由序号隔离。
打开业务面板时不做 60 秒自动业务刷新，避免覆盖教师或膳食人员正在核对的上下文。

## 5. 渲染与无障碍

同站点复用 `campus/vendor/three.module.js`、OrbitControls 和班级场景 `VisualKit`。
没有外部模型 CDN、照片、身份特征推断或整机安全策略修改。
八站的静态模型按材质及动作分组合批，合批后保留建筑拾取语义。
本期人物是装饰厨师/用餐形象，不绑定真实幼儿或员工考勤；没有自动播放加工/配送进度动画。
渲染按需发生，页面隐藏时暂停；WebGL 丢失后释放资源，普通八站操作仍可用。

按 1–8 可进入对应站，`/` 搜索业务物件，Escape 关闭面板；Tab 与原生控件可操作全部面板。
手机保留横向可滚动流程导航与底部抽屉，不产生整页横向溢出。
第 1 站周历在手机面板内部横向滚动并提示左右滑动，不改变整页宽度。


隔离工作树可用 `MEAL_SCENE_SOURCE` 在 Frappe 初始化之前指定本期源码。
浏览器脚本只使用临时 Chromium 用户目录与 localhost 合成数据，不使用个人 Cookie 或真实登录。
其合成 POST 覆盖采购需求草稿、班级餐次、食谱草稿及私有文件导入交互，不能表述为已在生产数据库写入实际单据。
真实站点脚本只输出汇总，并前后核对关键业务记录数量，最后 rollback；不输出学生姓名或健康信息。

## 8. 发布、回滚及后续

从 `586f881` 建立独立工作树实施和验收。发布只包含本功能文件以及角色入口、工作台按钮、缓存版本和文档。
不覆盖原有 `AGENTS.md` 删除、IDE 文件、其他脚本或下载包改动，不运行 migrate 或权限安装程序。
发布后使用已有 `deploy/classroom/refresh_runtime.py` 刷新 Frappe/网站缓存并优雅重载本 Bench Web 进程，
随后验证私有登录跳转、模块 MIME 和匿名接口拒绝。

回滚只回退本次提交的源文件及导航，按同样流程刷新缓存。没有数据库结构回滚；
正常使用后新增的采购需求或班级餐次仍是原业务记录，不得随页面回滚删除。

加工执行、特殊餐授权与交接、配送签收、留样/消毒、批次追溯和设备温度应分阶段单独定义。
任何新字段、DocType 或状态仍需单独预览结构、权限、历史处理和回滚，再取得明确授权，
不能为了实现效果图的数字而将任意 JSON/临时缓存冒充可审计的正式业务记录。
