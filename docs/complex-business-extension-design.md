# 未知复杂业务：受控明细、计算与原生复核机制

状态：设计审计与 v2 实现说明。2026-09-25。实际验收及未覆盖事项见 `unified-business-goal.md`；不以本设计文档代替验收。

## 推荐选择

在现有简单登记蓝图之外增加 **v2「明细计算与复核单」**：最多 2 张受控子表、服务端固定算子、固定 Frappe Workflow 模板。Codex 生成的是声明式业务方案，Tongjianyun 的版本化源码负责验证、安装和执行；左侧复用原生表单办理。

这是一个确实具有明细、计算、状态约束、复核和审计的可重复扩展机制，而不是多放几个普通字段就宣称“支持复杂业务”。但它仍不是任意复杂系统生成器：采购、财务过账、库存、工资、医疗决策和跨系统副作用必须复用原业务服务，或者另行开发受测试的源码适配器。

对操作人员仍保持简洁：右侧说需求 → 左侧看到方案与验证结果 → 点击确认启用 → 原业务表单填写/复核。开发、隔离验证、摘要校验和权限检查放在后台，不让用户操作配置文件。

## 1. 现有实现可以直接保留的部分

| 文件 / 方法 | 已有能力 | v2 应复用而非推翻 |
|---|---|---|
| `business_blueprints.py:validate_spec/propose/_load` | 严格白名单、私有方案、站点/所有者绑定、摘要 | 保持 v1 字段格式兼容；增加独立版本分支，未知键一律拒绝 |
| `business_blueprints.py:preview/activate/_state` | 显式确认、权限复核、同名冲突、实际表结构回读 | 升级为整个父表/子表/Workflow 包的核验，不能只核验父表 |
| `extension_policy.py` | 结构变更必须确认，禁止任意 DDL 与改上游 DocType JSON | v2 仍属于有边界的 `add-custom-business`；不因此开放 `add-doctype`、`database-ddl` 或上游结构修改 |
| `meal_views.py:selection/get_view/publish_for_task` | 只允许已注册视图、任务所有者执行、SSE 只发送选择、浏览器按自身身份回读 | 增强固定 `business_blueprint` 预览组件，启用后发布原生单据视图；不接受模型 HTML/SQL/JS |
| `frappe_project_views.py:native_view/operation_capabilities` | 原生表单嵌入、操作权限与原 Workflow 能力发现 | v2 父类型自动进入同一目录；子表不单独变成业务入口；办理与审批仍走原生界面 |

v1 仍拒绝任意 Table、公式和工作流；v2 通过单独的可信源码模块生成受控子表、固定计算与原生复核，未开放任意元数据或表达式。

## 2. 先复用，再创建：必须执行的分流

1. 以当前站点用户身份检索全部已安装应用的 DocType、子表、Workflow、报表与业务方法，不只检索童健云的常用清单。
2. 如果现有类型和原服务能够办理，生成“业务编排选择”：打开原表单/报表，传递经过校验的目标或筛选。不要创建同义类型。
3. 如果只是缺少组合展示，添加注册业务视图，数据仍从原系统读取；不要复制业务数据为一张新表。
4. 只有需求确实是独立的登记/明细估算/复核记录，且不产生专业系统副作用，才允许 v2 蓝图。
5. 需要过账、库存移动、复杂权限、跨单据补偿、定时执行、外部 API 或非固定计算时，进入源码适配器开发；未实现前清楚说明缺口，不把 v2 当替代品。

方案预览应记录简短复用判断，例如：“现有采购申请会进入物料流程；本方案仅记录活动估算与内部复核，不创建采购或会计凭证。”该判断必须来自实际元数据核验，不接受模型凭空断言原业务不存在。

## 3. 最小声明式能力

建议将 v2 的变化限定为下表，具体 JSON 命名可由实现调整，但语义不可扩张。

| 能力 | 最小支持 | 明确拒绝 |
|---|---|---|
| 主表 | 现有安全字段、必填标题、自动历史记录；可提交 | 模型指定 DocType 名称、权限规则、角色创建、默认 Python 表达式 |
| 子表 | 最多 2 张，每张最多 12 个安全字段；单表实例最多 500 行；命名由安装器确定 | 子表嵌套、任意既有子表重用/改写、模型指定底层表名、独立子表权限接口 |
| 行计算 | `multiply`：同一行两个数值字段相乘，写入指定只读数值字段 | 字符串表达式、函数名、属性访问、动态 import、eval/safe_eval |
| 汇总 | `sum`：指定子表数值列汇总到主表只读数值字段 | 跨记录 SQL、跨表查询、税率/汇率/会计规则推导、隐式外部数据 |
| 复核 | 固定的“草稿→待复核→已通过/退回”及已通过后撤销；原 Frappe Workflow | 任意 transition condition/update expression、Webhook、Server Script、transition task、自动通知 |
| 权限 | 初始仅现有 System Manager 角色；明示办理/复核范围 | 新建角色、给已有用户加角色、共享管理员凭据、模型指定 `ignore_permissions` |
| 版本 | 新方案摘要固定，启用对象与规则完全对应 | 自动迁移已有表、覆盖同名业务、改已发布方案后静默沿用旧确认 |

方案格式示例（只声明方案，仍须预览和明确确认才能启用）：

```json
{
  "version": 2,
  "key": "activity_estimate_demo",
  "title": "示例活动筹备估算单",
  "description": "仅记录明细估算与内部复核，不产生采购、付款或库存动作。",
  "fields": [
    {"fieldname": "activity_day", "label": "活动日期", "fieldtype": "Date", "reqd": 1},
    {"fieldname": "estimated_total", "label": "估算合计", "fieldtype": "Currency"}
  ],
  "tables": [
    {
      "fieldname": "estimate_lines",
      "label": "估算明细",
      "fields": [
        {"fieldname": "item_description", "label": "明细说明", "fieldtype": "Data", "reqd": 1},
        {"fieldname": "quantity", "label": "数量", "fieldtype": "Float", "reqd": 1},
        {"fieldname": "planned_rate", "label": "计划单价", "fieldtype": "Currency", "reqd": 1},
        {"fieldname": "estimated_amount", "label": "估算金额", "fieldtype": "Currency"}
      ]
    }
  ],
  "calculations": [
    {"op": "multiply", "table": "estimate_lines", "sources": ["quantity", "planned_rate"], "target": "estimated_amount"},
    {"op": "sum", "table": "estimate_lines", "source": "estimated_amount", "target": "estimated_total"}
  ],
  "workflow": {"template": "review"}
}
```

计算输出的 `read_only` 由可信安装器推导，不由模型自行控制。`workflow_state` 等保留字段也由安装器提供，不能被输入字段占用。整个 v2 类型、实例行数、数值范围、文本长度、总请求大小必须有上限。

该例中的金额只是指定单一计量口径下的估算；不做汇率、税务、成本核算或会计凭证。若没有明确币种与精度，只能显示估算数值，不能宣称是可支付金额。

## 4. 激活必须安装并核验整个包

一个 v2 方案应确定以下不可拆分的对象清单：

- 1 个自定义父 DocType，`custom=1`、`track_changes=1`；启用复核时 `is_submittable=1`。
- 0–2 个自定义子 DocType，`istable=1`；仅对应本方案父表的 Table 字段。
- 固定的工作流状态字段、父表权限、只读计算字段、计算精度约束。
- 0–1 个安装器生成的 Workflow，以及其明确需要的状态/动作元数据。
- 激活清单：父类型保存规范化 v2 方案与摘要（Base64 编码，不是签名），子表和工作流名称由方案确定。私有原方案另绑定站点/所有者，类型审计评论记录方案 ID。普通第二位复核人无需读取提出者的私有文件。底层数据库或可信服务器代码的特权修改不属于应用身份隔离边界。

### 名称、权限与冲突

子表与 Workflow 名称必须由可信代码根据业务 key 和子表 key 确定，并满足数据库名称长度约束。禁止接受用户提供任意 DocType/表名。安装前必须核验全部目标名，不仅父表名。

初始仅使用现有 System Manager，给新类型配置最小的 read/create/write/submit/cancel 等明确需要的权限，不给删除和自动角色管理权限。还要核验操作者具有创建 Workflow、必要状态/动作对象的元数据权限；不能以仅有 `DocType.create` 代替整个安装包授权。

已有同名对象只有在全部定义与所有权指纹完全匹配时才能作为重复确认返回既有结果；其余情况是冲突，不得覆盖。Workflow 只能绑定此方案全新父类型，不能挂到既有专业单据。

### DDL 与部分失败

MariaDB DDL 及 Frappe 元数据提交不保证整体事务回滚。需要显式记录：`proposed → validating → activating → active`，异常为 `incomplete/conflict`，而不是笼统说“创建失败，已回滚”。

只有父表、子表的物理列、DocField/DocPerm、Table.options、Workflow 状态/转换和激活清单全部一致，才能返回 `active`。部分完成后保留证据和已有对象，不自动 drop，不删表重试。最小版本可以要求管理员检查；若后续加入续装，只能在同一摘要、同一所有者、已完成对象完全匹配的前提下补缺失对象。

## 5. 服务端运行时：统一钩子，但严格限定作用域

可以在 Tongjianyun 注册 `doc_events['*']`，但这是敏感全局入口，应遵循：

1. 非本机制的 DocType 立即返回；不得改变其他应用的行为。
2. 本命名空间内先加载可信的“已激活清单”，验证父类型、子类型、规则摘要、引擎版本和当前元数据指纹。只凭名称前缀或可修改的 description 不足以授权执行。
3. manifest 缺失、被改动、表结构漂移或 Workflow 被替换时拒绝该扩展的写入并提示检查；不能默默跳过计算后保存。
4. 激活后的运行清单与用户的待审私有方案分离。不能依赖“只有原方案所有者能 `_load`”来运行所有记录，也不能让其他业务用户读取私有方案正文。
5. 不依赖客户端传来的目标类型、公式、字段属性、汇总值、状态或权限标记。所有规则从已验证清单获取。

数值运算使用 `Decimal` 和确定的量化/舍入规则。明确空值、零、负数、精度、上限和溢出处理；拒绝 NaN/Infinity、字符串表达式及循环依赖。每个计算目标只能有一个生产者；行计算先完成，再执行汇总。不能同时让用户输入与计算规则竞争同一字段。

`read_only` 只是界面属性，不是安全边界。通过原生表单、REST、Data Import 或 Document 保存时都必须服务端重算。子表类型、字段归属、行 ID 和父记录归属必须校验，不能因模型提供的 child doctype/name 接受其他表或其他父记录的行。

推荐在 `before_validate` 做草稿/提交路径的确定性计算；在 `validate` 校验 Workflow 跳转和输入冻结；在 `before_update_after_submit` / `before_cancel` 核验已提交记录不可被夹带改动。不要在撤销时将历史明细按新的规则重算。审批通过后业务输入和计算结果保持不可编辑；如果要修订，后续设计显式修订流程，而不是恢复为草稿偷偷重写。

## 6. 保留原 Workflow，补上直接保存的边界

原 Frappe 负责状态机、角色、提交/取消、审计评论与原生按钮；本机制只生成固定、经过验证的模板，不另造一套平行审批引擎。

| 当前状态 | 操作 | 下一状态 | docstatus |
|---|---|---|---|
| 草稿 | 送审 | 待复核 | 0 → 0 |
| 待复核 | 通过 | 已通过 | 0 → 1 |
| 待复核 | 退回 | 退回 | 0 → 0 |
| 待复核 | 撤回 | 草稿 | 0 → 0 |
| 退回 | 再次送审 | 待复核 | 0 → 0 |
| 已通过 | 撤销 | 已撤销 | 1 → 2 |

不能把未提交记录的“撤回”变成 `docstatus=2`；原 Frappe 不允许草稿直接取消，也不允许已提交记录回到草稿。所有业务输入只能在草稿/退回状态修改。待复核时修改输入需要先撤回/退回，防止复核对象在审批中悄然变化。

### 本次源码审计发现的必要加固

已读取服务器上的 `frappe/model/workflow.py` 与 `frappe/workflow/doctype/workflow/workflow.py`：

- `apply_workflow()` 会调用 `has_approval_access()`；`validate_workflow(doc)` 的直接状态改变会检查可用转换，但没有同样调用自审限制。因此不能只隐藏按钮或只依赖 `apply_workflow`：本扩展钩子必须对所有状态变化，基于保存前记录、原转换和当前用户，再校验 `has_approval_access`，并拒绝非法初始状态、直接跳级或状态/docstatus 不匹配。
- `has_approval_access()` 明确允许 `Administrator` 例外。初始角色都是 System Manager 并不等于职责分离；即使 `allow_self_approval=0`，也不能把 Administrator 自审演示说成“四眼审批”。验收至少需要两个独立 System Manager 用户及一个无权用户。
- `Workflow.on_update()` 可能补建 Custom Field 并更新空状态；`set_active()` 会停用同 DocType 的其他流程。应在新父表中预声明状态字段、只对本机制新类型创建流程、事前检查不存在其他流程，避免安装时影响既有业务。
- 原 Workflow 支持 `condition`、`evaluate_as_expression`、`update_field`、`transition_tasks`，包括 Webhook/Server Script。v2 模板必须将这些能力固定为空/禁用，JSON 不得透传。默认关闭邮件通知。

对于可能将“状态迁移”与“业务字段改动”夹在同一次 REST 请求中的情况，先比较原记录的业务输入：待复核→通过/退回/撤回、已通过→撤销都不得夹带明细修改。仅在原表单保存了草稿、原服务完成重算后才可送审。

## 7. 可复现的开发到办理链

| 阶段 | 可信产物 / 动作 | 可向用户宣称什么 |
|---|---|---|
| 识别 | 已安装元数据检索、现有业务复用结论 | 已找到原业务，或确定一个具体缺口 |
| 开发 | 版本化引擎/适配器源码、方案 JSON、边界测试；保留用户现有改动 | 已生成候选方案，不说业务已上线 |
| 隔离验证 | 独立空数据库/Redis、确定引擎版本与方案摘要、合成记录的生命周期结果 | 模板机制已验证；若该方案也实际跑过，则单独注明本方案验证通过 |
| 预览 | 左侧展示主字段、子表、计算口径、固定状态流、角色、结构与副作用影响 | 等待用户确认启用；不自动调用 activate |
| 确认 | 当前用户的 POST，绑定 site/owner/proposal/digest；全包权限与冲突再核验 | 用户已确认当前版本，开始安装 |
| 启用 | 原 ORM/schema 安装、物理结构和 Workflow 回读；注册原生入口 | 业务类型已可用，但尚未录入/审批业务记录 |
| 办理 | 场景内原生表单新增明细、保存、送审、另一个合格用户复核 | 每个动作只根据真实返回和回读描述 |
| 验证 | 新连接回读、权限拒绝、历史/审计与最终状态 | 已完成被测试的具体流程，不扩大为任意业务全覆盖 |

验证报告不能由模型写一个 `passed=true` 冒充。至少记录受控测试程序版本、引擎/方案摘要、隔离站点标记、实际对象和测试断言；生产启用前核对报告与当前版本的一致性。通用引擎测试通过与特定方案验收通过分开记录。

左侧无需实现另一套动态应用框架：方案阶段用固定预览组件；启用后复用 `frappe_doctype` / `frappe_new` / `frappe_document`。新业务目录和能力查询自动来自 Frappe 元数据。聊天阶段输出说明“正在验证结构”“等待确认”“已启用”“已回读记录”，不发送任意前端代码。

## 8. 最小真实验收样例

仅在现有专属验收站点 `unified-business-acceptance.localhost` 执行；继续使用独立 loopback 数据库/Redis，不复制生产数据。示例业务名为“示例活动筹备估算单”，明确不等于采购单、预算审批或付款凭证。

合成明细：第一行数量 `2.5`、计划单价 `3.8`，金额 `9.50`；第二行数量 `10`、计划单价 `1.25`，金额 `12.50`；服务端合计 `22.00`。

最低通过条件：

1. Codex 工具生成并发布该 v2 方案；原 v1 方案完整回归不退化。
2. 预览前不新增 DocType；非所有者、摘要过期、无建模权限、取消中的任务均不能启用。
3. 明确确认后真实创建父表、子表和 Workflow；验证物理 schema，而不是只看 DocType 记录存在。
4. 重复启用不重复建表；任一同名冲突/子表缺失/Workflow 漂移均失败并保留证据；中途失败不自动删表。
5. 当前用户在统一场景原生表单新建，两行真实保存；只读计算字段显示并回读为 `9.50 / 12.50 / 22.00`。
6. 原生 REST/Document 提交伪造金额时由服务端纠正或拒绝；非法数值、循环引用、未知字段、恶意子表类型/归属/重复行 ID 均拒绝。
7. 草稿修改明细后重新计算；Version/审计能反映变更，不把模型文本当数据结果。
8. 申请人送审；本人自审按策略拒绝，第二个 System Manager 通过。单独记录 Administrator 的原生例外，不称为职责分离验证。
9. 直接 REST 保存 `workflow_state`、直接 `submit()`、错误 docstatus、首次插入“已通过”均不能绕过规定状态和自审校验。
10. 待复核时夹带改明细、已通过后改行或总额、撤销后再修改均拒绝；退回→改草稿→再次送审成功。
11. 原生取消把已通过变为已撤销；未提交记录不能直接取消；不触发库存、付款、邮件或外部服务。
12. 无权用户不能列出或读取记录；子表不能独立作为主业务访问。普通 Frappe 记录不受通配钩子影响。
13. SSE 展示请求与浏览器真实加载分别记录；原生表单保存、审批按钮和新连接回读形成浏览器到数据库端到端证据。

只做 ORM 测试而没有浏览器实际保存，应明确写“数据库生命周期通过，浏览器提交待验收”；只看到表单和按钮，不能写“复杂业务办理已通过”。

## 9. 仍必须走源码适配器的业务

固定算子与固定复核之外，不继续向 JSON 添加表达式、任意方法名或动态执行能力。新增能力应落在 `tongjianyun` 的版本化 Python/前端注册组件中，包含明确输入模型、目标原服务、权限、幂等、并发、审计和验收程序。

例如采购→收货→库存，应编排 ERPNext 原 Material Request/Purchase Order/Purchase Receipt 及其现有校验/Workflow；财务应走原会计单据；食谱继续每周唯一与既有保存服务。这些适配器可以被 Codex 自行开发和测试，但生产部署、结构变更与高影响业务操作仍遵循既有确认边界。

本方案不修改上游 Frappe/ERPNext 源码，不开放浏览器任意 HTML/JS/SQL，不在生产测试数据写入，不把“有源码能力”当作“已经完成开发→预览→确认→办理→回读验收”。
