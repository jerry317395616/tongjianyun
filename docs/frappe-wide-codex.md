## 全站点业务发现

按实时已安装应用和模块元数据发现业务，逐项执行当前账号权限检查，而不是把新业务继续手工加进固定清单。

## 原生页面与操作

业务目录按应用 → 模块 → 单据、报表、页面、工作区展开。也支持用原始名称/现有中文翻译检索；中文翻译复用 I-ONE/site 现有字典。

打开业务时，左侧显示同站点的原生 Frappe 页面，并提供“在独立页面打开”入口。这样无需复制已有的表单、新建、编辑、提交、审批及报表筛选实现；这些操作仍由原应用校验权限和工作流。

仅打开页面不等于已经获取报表结果、创建单据或完成审批。Codex 处理具体写操作时应先核验对象、账号、业务服务和工作流；不能用服务器 root 权限、`ignore_permissions` 或 SQL 绕过业务权限。影响资金、取消单据、批量覆盖、删除等操作需要明确的对应用户指令。

普通网页用户没有因此获得管理员对话权限。入口仍只允许原有 Administrator/System Manager；每个站点业务另查原角色、模块启停、单据、报表、记录权限。目录和模型仅收到业务入口元数据；原生页面直接加载数据，不把配置、密钥、病史或薪酬明细复制进对话。

## 已登记调用

- `project_catalog`：服务器项目/目录与安装状态说明。
- `frappe_catalog`：全站点业务；可筛选 `app / module / kind / keyword / offset`。
- `frappe_doctype`：原生列表或单例设置表单。
- `frappe_document`：先检查目标记录读取权限，再打开原生表单。
- `frappe_report`：原报表角色、引用类型权限及自定义报表检查。
- `frappe_page`：原 Page 使用权限。
- `frappe_workspace`：原 Workspace 的角色、模块及个人范围。

不允许自定义 URL、跨站点参数、SQL、HTML 或任意脚本进入画布。原生地址由服务器核验元数据后构造，并由前端限制为 `/desk/` 相对地址。

## 测试与限制

- 50 项 Python 测试及 20 项前端组件/会话测试通过。
- 全量元数据探针验证 662 + 233 + 24 + 38 个原生路由，零路由生成失败；不批量执行报表、不创建测试业务记录。
- 访客访问被拒绝；现有受限管理账号只得到其可见的 528 个入口，单据类型逐一核对读取权限。
- 原生页面打开与实际业务处理分别验证。不能把路由验证当作全部业务流程、所有第三方接口、每个报表参数组合均已端到端测试。
- 原始膳食工作台 URL 实测：默认周食谱和历史对话保留；右侧真实 SSE 对话核验 Codex 工作目录为 `/home/zyd/frappe`，并显示 7 应用全站目录；应用 → ERPNext → 资产 → Asset 的原生页面成功内嵌，原页面、元数据与列表请求均为 HTTP 200，没有创建测试业务记录。
- 目录摘要区分应用分组、模块分组和业务明细，避免模型把未在当前层级显示的明细说成已经展示。
- 同一对话续接实测：Codex 先搜索 ERPNext 报表元数据，再发出 SSE 视图事件，左侧成功打开 Fixed Asset Register 原生报表及筛选项。只验证页面与查询链路，不声称完成了资产统计。
- 仅有源码、未安装/未部署的项目需要先按具体目标接入；其他站点需要独立身份及访问配置。不存在的厨房配送、留样等业务不会凭空变成已有数据。
- 所有集成代码位于 Tongjianyun 扩展应用，未改动上游应用、DocType 结构、AppArmor、安全策略或凭据。
