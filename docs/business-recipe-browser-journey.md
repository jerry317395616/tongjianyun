## 实际原因与候选修复

原 `FrappeBusinessQueue.ready()` 将最后心跳超过 120 秒的进程判为不健康，但服务器
实际安装的 RQ 默认 worker TTL 为 420 秒、空闲 dequeue 阻塞 405 秒；每轮阻塞前后
才更新 heartbeat。该判断会周期性拒绝健康的空闲 worker。

同一个实际存活 worker PID 2389082 的观测：

| 观测 | 结果 |
| --- | --- |
| 队列及状态 | 精确 business_codex 队列，idle |
| 心跳年龄 / Redis 剩余有效期 | 396.938 秒 / 83 秒 |
| 原检查 | false |
| native launcher / 开关 / 密钥结构校验 | true / true / true，不输出密钥 |

随后保持同一进程、同一队列且不提交任务，在单独测试进程加载候选服务模块：心跳年龄
377.166 秒、TTL 103 秒时，原代码返回 false，候选代码返回 true。
这证明健康检查差异，不是模型执行或业务保存的证明。

候选改动：

1. 使用 RQ 自身正数 Redis 有效期，同时验证有效且非未来的 heartbeat、idle/busy 状态、
   精确队列。不存在、已过期或没有过期时间的 worker 不算健康。此检查仅是准入提示，
   绝不作为任务退出、取消成功或数据库事务结束的依据。
2. 显式执行器/模型配置/队列未就绪返回固定 `503 + business_error_code=service_unavailable`，
   不伪装成账号失效。原登录检查仍在先，真实会话权限拒绝仍为原 403。
3. 503 不标记“从未接收”：同一个请求编号可能已被早先接受。页面保留请求编号与已上传
   File，先恢复已有记录，只有用户明确再次发送才重用原请求，不自动重发或重新上传。
4. 业务模式的通用 400/422 不再丢掉未确认请求；只有可信、明确的未接收标记才解除该约束。
